# Supporting pi — investigation

This is the study behind pi support, written to the same standard as
[`formats.md`](formats.md): what was verified, what was derived from source, and
what is still unknown. It covers both directions — pi as a fourth *source*
Ossuary reads, and pi as a third *host* Ossuary ships a plugin for.

**The source half shipped**; `adapters/pi.py` and the format record in
[`formats.md`](formats.md) are the result, and this document is kept as the
reasoning behind it. **The host half did not** — see
[Decision](#decision-the-adapter-alone).

Verified date: 2026-07-28.

pi is a coding agent CLI (`pi`), docs at pi.dev. The package and repository moved
while this was written and both names are in circulation:

| | Old | Current |
|---|---|---|
| npm | `@mariozechner/pi-coding-agent` 0.73.1 | `@earendil-works/pi-coding-agent` 0.82.1 |
| repo | `badlogic/pi-mono` | `earendil-works/pi-mono`, `earendil-works/pi` |

Both releases were unpacked and read. The session format is identical between
them apart from two additive fields (`retainedTail` and `usage` on compaction
entries, `usage` on tool results). Facts below come from `dist/` sources and the
shipped `docs/session-format.md`, plus session files generated by pi's own
`SessionManager` (see [Fixtures](#fixtures)). **No real pi conversation was
available on this machine — there is no `~/.pi` here** — so this is the same
evidence class as the Codex adapter, one notch better: the fixture bytes are
written by the real writer, not by hand.

Verdict: pi is the *easiest* of the four formats to normalize, and the only one
that carries a structure `NormalizedEvent` cannot currently express — a
conversation tree. One decision (below) has to be made before any code is
written; everything else is mechanical.

Scope: **the adapter is the whole of pi support.** The host half was investigated
and deferred — a pi user reads their pi sessions from Claude Code or Copilot,
using the plugin that already ships. The reasoning is in
[Decision](#decision-the-adapter-alone).

## Layout and discovery

```
~/.pi/agent/sessions/--<cwd>--/<timestamp>_<uuid>.jsonl
```

`<cwd>` is the working directory with the leading separator stripped and every
`/`, `\` and `:` replaced by `-`, wrapped in `--` on both sides
(`/home/user/ossuary` → `--home-user-ossuary--`). `<timestamp>` is the session's
ISO creation time with `:` and `.` replaced by `-`.

Overrides, in the order pi resolves them:

| Mechanism | Effect |
|---|---|
| `PI_CODING_AGENT_DIR` | replaces `~/.pi/agent` (tilde-expanded) |
| `PI_CODING_AGENT_SESSION_DIR` | replaces the sessions directory |
| `sessionDir` in `~/.pi/agent/settings.json` | same, from config |
| `pi --session <path\|id>` | one session anywhere on disk |

The env var *names* are derived at runtime from `piConfig.name` in pi's own
`package.json` (`${APP_NAME.toUpperCase()}_CODING_AGENT_DIR`), and the config
directory name from `piConfig.configDir`. A rebranded build named `tau` reads
`TAU_CODING_AGENT_DIR` and stores under `~/.tau`. Ossuary should honour the `PI_`
spelling and not attempt to chase rebrands.

Discovery should glob `**/*.jsonl` under whichever sessions directory resolves,
exactly as the Claude Code adapter does, rather than hardcoding the two-level
depth. `project` comes from the header's `cwd` field, which is the real path —
better than decoding it back out of the directory name, which is lossy (`-` is
not reversible into `/`, `\` or `:`).

### `claims()`

The first line of every pi session is a header with `type: "session"` and a
`cwd`. That is unambiguous, and it does not collide with anything already
registered:

- Codex's sniff wants `session_meta`, or `payload` + `type` + `timestamp`; a pi
  header has no `payload`. **This turned out to be not quite enough.** The sniff
  reads several lines, not just the first, so a pi entry carrying a `payload` key
  anywhere in the head of the file — an extension's `custom` entry, or a future
  entry type — reads as a rollout line and Codex claims the transcript too. The
  fixtures caught it. Codex now stops at a pi header (`type: "session"` with a
  `cwd`) the same way it already stops at Claude Code's `sessionId`.
- Claude Code's sniff wants `sessionId`, or `message` + `uuid`; pi message
  entries carry `message` + `id`, never `uuid`. It does not claim pi files.
- Copilot claims by filename (`events.jsonl`) or a `.json` VS Code document.
  Neither matches `<timestamp>_<uuid>.jsonl`.

So today every pi transcript is discovered by nobody, and adding the adapter
takes no sessions away from another one.

## Line schema

Each line is one JSON object with a `type`. Entries after the header form a tree
via `id` (8-char hex) and `parentId` (`null` on the first entry).

```json
{"type":"session","version":3,"id":"019faadf-…","timestamp":"2026-07-28T22:37:06.777Z","cwd":"/home/user/demo"}
{"type":"model_change","id":"cbda498b","parentId":null,"timestamp":"…","provider":"anthropic","modelId":"claude-sonnet-4-5"}
{"type":"message","id":"bf7ee0b3","parentId":"9d95fe37","timestamp":"…","message":{"role":"user","content":"run the tests","timestamp":1785278226778}}
```

Entry types and the mapping that fits Ossuary's model:

| Entry `type` | → kind | Notes |
|---|---|---|
| `session` | — | header; source of `session_id` (`id`), `project` (`cwd`), `parentSession` |
| `message` | depends on `message.role` | see below |
| `model_change` | `meta` | mid-session model switches: a real signal, and one no other source records |
| `thinking_level_change` | `meta` | reasoning level changed mid-session |
| `compaction` | `meta` | carries `summary`, `tokensBefore`, `firstKeptEntryId` and/or `retainedTail` |
| `branch_summary` | `meta` | the user rewound; `fromId` names the abandoned leaf |
| `custom` | `meta` | extension state, never in LLM context |
| `custom_message` | `message` | extension-injected context, `display` says whether the user saw it |
| `label` | `meta` | bookmark on `targetId` |
| `session_info` | `meta` | user-set display name |

`message.role`:

| Role | → kind / role | Notes |
|---|---|---|
| `user` | `message` / user | `content` is a string or `(text\|image)[]` |
| `assistant` | one event per content block | `text` → `message`, `thinking` → `thinking`, `toolCall` → `tool_call`. Carries `provider`, `model`, `usage`, `stopReason`, optional `errorMessage` |
| `toolResult` | `tool_result` | `toolCallId`, `toolName`, `content`, `isError`, optional `details`, `usage` |
| `bashExecution` | `tool_call` + `tool_result` | the user's own `!command`; has `command`, `output`, `exitCode`, `cancelled`, `truncated`, `fullOutputPath` |
| `custom` | `message` | extension message (`hookMessage` in v2 files) |
| `branchSummary`, `compactionSummary` | `meta` | summary roles |

One line becoming several events is already how the Claude Code adapter works,
so an assistant message with a thinking block, a text block and two tool calls
is four events, and `index` stays an ordinal over events.

**Tool calls and results pair by `toolCallId` against the call's `id`**, never
positionally — same rule as everywhere else. Results are adjacent in practice
because pi appends them in completion order, but nothing guarantees it.

### On-disk versions

The header carries `version`. pi migrates old files to v3 *and rewrites them* on
load, so any session opened by a recent pi is v3. Files never reopened stay as
they were, and the adapter has to read all three:

- **v1** — linear; no `id`/`parentId` at all; compaction uses
  `firstKeptEntryIndex` (an integer index) instead of `firstKeptEntryId`.
- **v2** — the tree; the extension message role is spelled `hookMessage`.
- **v3** — current; `hookMessage` renamed to `custom`.

Treating a missing `id` as "linear, parent is the previous entry" covers v1
without a separate code path.

## The one real decision: the tree

pi sessions branch in place. `/tree` and `/rewind` move the leaf back to an
earlier entry and append from there, so **file order is not conversation order,
and some entries on disk are on no path at all.** In a session generated for this
investigation, entry `eaf90385` (a `branch_summary`) has `parentId` pointing at
an assistant message five lines above it, which orphans the five entries in
between — a tool result, a bash execution, a compaction, a session name and a
label. All of them are still in the file.

The active path is recoverable: pi's leaf on load is the **last entry in the
file**, so walking `parentId` from the last line to the root gives the live
conversation, and everything else was abandoned.

The recommendation follows the rule the project already committed to — *no line
is ever rejected, whatever is on disk is the only record that will ever exist*:

1. Emit **every** entry, in file order. `index` stays the file ordinal, so
   `evidence_event_indices` remain stable and mean what they say.
2. Put `entry_id`, `parent_id` and `off_path` in `meta`. Recorded only when
   true: absence means the entry is on the live conversation, which is the
   common case and the one that needs no flag.
3. Surface off-path entries in the outline. Abandoned branches are not noise —
   a user who rewound is a user whose agent went somewhere useless, which is
   exactly the failure class Ossuary exists to cluster.

Point 3 is the only change outside the adapter: `outline._flags` is a fixed,
shared vocabulary (`E T R X P O S ~`), so a `B` for "off the active path" is a
change to every source's legend. It is small, but it is a decision about the
shared surface, not a private adapter detail, and it should be made
deliberately. It was: `B` is in the legend, and the explanatory line only
appears for sessions that actually branched.

The alternative — emit only the active path — is cheaper and wrong: it would
silently delete the evidence that a rewind happened, and a session that lost
five events between two adjacent indices would read downstream as a session
where those things never occurred.

## Shape records

| Field | Where it comes from | Quality |
|---|---|---|
| `byte_length`, `content_hash`, `is_empty`, `terminates_cleanly`, `is_round_number` | the result text | as elsewhere |
| `duration_ms` | `toolResult.timestamp` − the assistant message's `timestamp`, both Unix ms | `derived`; pi records no per-tool duration |
| `exit_code` | `bashExecution.exitCode` only | genuinely recorded, but only for the user's own `!` commands |
| `has_error_field` | `toolResult.isError` | recorded |

Two notes that matter more than they look:

**Do not parse the bash tool's exit code out of its text.** When a command exits
non-zero the bash *tool* throws, and the string `Command exited with code N` ends
up appended to the result payload. That number is real, but recovering it means
regex-matching a human-readable sentence that changes between releases, and a
wrong parse is indistinguishable from a recorded code — the exact failure mode
`_exit_code_for` exists to avoid in the Claude Code adapter. `has_error_field`
already carries the signal. Leave `exit_code` null and let the text speak.

**pi reports its own truncation, numerically.** Tool output is cut at 2000 lines
or 51200 bytes (whichever hits first), the payload gets a human-readable marker
appended (`[Showing lines 1-120 of 9000. Full output: /tmp/…]`), and
`details.truncation` carries the exact numbers:

```json
{"truncated":true,"truncatedBy":"bytes","totalLines":9000,"totalBytes":900000,
 "outputLines":120,"outputBytes":51188,"lastLinePartial":false,
 "firstLineExceedsLimit":false,"maxLines":2000,"maxBytes":51200}
```

No other supported CLI does this. It is worth carrying into `meta` verbatim: it
turns "this payload looks capped" into "this payload *was* capped, from 900000
bytes, by the byte limit". It also means the 51200-byte cap will show up in
`ossuary_tool_stats` as a recurring length across the corpus, and
`is_round_number` fires on it (51200 is a multiple of 1024), which is correct.

Note that pi's marker and `[[ossuary:elided N of M bytes]]` are different claims:
pi's says the *CLI* cut the output before the model saw it; Ossuary's says
*Ossuary* cut it before the agent saw it. Both can be present. Neither should be
stripped.

## What pi records that nothing else does

Worth capturing in `meta` even though no existing field wants them:

- `usage` per assistant message — input/output/cache tokens **and cost**, plus
  `usage` on tool results (nested LLM work) and on compactions.
- `stopReason` — `stop`, `length`, `toolUse`, `error`, `aborted` — with
  `errorMessage`. A turn that ended at `length` or `aborted` is a health signal
  available nowhere else in the corpus.
- `tokensBefore` on compactions.
- `cancelled` and `fullOutputPath` on bash executions.
- `model_change` entries: the model changed mid-session, which reframes every
  event after it.

### Caveat: `meta` is currently invisible to the agent

`store._render_event` prints role, kind, tool, ts, the shape line, parse errors
and the `orphan_result` note — and then the body. **Nothing else in `meta` is
rendered anywhere.** So everything in the list above, plus `truncation` and
`on_active_path`, reaches the agent only if it is deliberately surfaced: into the
event text, into an outline flag, or by extending `_render_event`.

This is not a pi-specific problem — it is where the pi work would collide with an
existing limit. Decide it with the tree question, since both answers land in the
same place.

## Fixtures

Unlike Codex and Copilot, the fixture does not have to be hand-written to a
schema read out of source. pi exports `SessionManager` from its package root, so
a fixture can be produced **by pi's own writer**, with no model, no API key and
no network:

```js
// npm i @earendil-works/pi-coding-agent
import { SessionManager } from "@earendil-works/pi-coding-agent";
const sm = SessionManager.create("/home/user/demo", "tests/golden/pi/sessions/--home-user-demo--");
sm.appendModelChange("anthropic", "claude-sonnet-4-5");
sm.appendMessage({ role: "user", content: "run the tests", timestamp: … });
const asst = sm.appendMessage({ role: "assistant", content: [
  { type: "thinking", thinking: "check the suite" },
  { type: "toolCall", id: "call_1", name: "bash", arguments: { command: "pytest -q" } },
], provider: "anthropic", model: "claude-sonnet-4-5", usage: {…}, stopReason: "toolUse", timestamp: … });
sm.appendMessage({ role: "toolResult", toolCallId: "call_1", toolName: "bash", … });
sm.branchWithSummary(asst, "tried approach A, abandoned");   // orphans everything after `asst`
```

That was run for this investigation and produced the branching session described
above. The generated file should then be edited by hand to add what pi will never
write — a malformed line, an orphaned tool result, a payload at exactly the byte
cap — the same deliberate damage the other golden fixtures carry.

A v1 and a v2 fixture are also worth having, since pi will never write them again
and they are the shapes most likely to break a parser written only against v3.

## Cost

What it took, as built:

| Change | Size |
|---|---|
| `src/ossuary/adapters/pi.py` | ~450–550 lines, closest sibling is `codex.py` |
| `Source` literal in `models.py`, registry in `adapters/__init__.py` | 2 lines |
| `tests/golden/pi/…` fixtures (v3 + branch, v2, v1) | generated, then damaged by hand |
| `tests/test_adapters_pi.py`, `conftest.py` fixture | ~150 lines |
| `tests/test_discovery_and_cli.py` — the assertions that enumerate the sources, plus `test_all_four_fixtures_are_found` (name and count) | ~4 lines |
| `docs/formats.md` — a pi section | ~60 lines |
| `README.md` — one `--source` line | 1 line |
| Both plugins' `investigate/SKILL.md` — the sentence naming the three CLIs | 2 lines |
| Outline flag + legend, if the branch flag is adopted | ~6 lines, shared surface |

No `SCHEMA_VERSION` bump: `NormalizedEvent` does not change shape, and adding a
`Source` value does not invalidate cached artifacts derived from the other three.

Everything else is already source-agnostic — `ALL_SOURCES` drives the CLI, the
MCP server, the store and the report, so nothing downstream needs to learn the
word "pi".

## Unknowns

- **No real corpus.** Every claim here is from pi's source, its shipped docs, and
  files written by its own `SessionManager`. A real session on a real machine
  may contain shapes none of those produce. When a real file disagrees with this
  document, the file wins.
- **Image content blocks are base64 in-line.** A session with pasted screenshots
  will carry megabytes of base64 in `content`. Codex names non-text items
  (`[input_image]`) rather than inlining them; pi's adapter should do the same,
  or every shape record on those events measures base64 rather than payload.
- **`custom` / `custom_message` entries are open-ended.** Extensions choose
  `customType` and the shape of `data`. They must degrade to `meta` events
  carrying stringified JSON, never to a parse failure.
- **Which timestamp to trust.** Entries carry an ISO `timestamp` and the message
  inside carries a Unix-ms `timestamp`. They are written microseconds apart by
  the same process, but only the ms one is precise enough for tool durations. It
  is also unverified whether the assistant message's timestamp is stamped when
  the turn starts streaming or when it completes — which decides whether a
  derived duration includes the model's own generation time. That needs a real
  session with a slow tool call to settle, and until it is settled the duration
  is `derived` and the outline says so.

# pi as a host

**Investigated and deferred — see [Decision](#decision-the-adapter-alone) at the
end of this section.** pi sessions are readable from Claude Code or Copilot the
moment the adapter exists, which is what "supporting pi" needs to mean for now.
This is the record of what the other route would have cost.

pi has a plugin system, and most of the Ossuary plugin ports into it unchanged.
Two things do not, and they are the two the plugin is built on.

> pi "intentionally does not include built-in MCP, sub-agents, permission popups,
> plan mode, to-dos, or background bash. You can build or install those workflows
> as extensions or packages."
>
> — `docs/usage.md`, Design Principles

So the honest answer to *can it be identical to the Claude Code and Copilot
plugins* is **no** — not in the sense of shipping the same manifest and the same
two markdown files and being done. The user-facing experience can be made to look
the same. Getting there means writing an extension, because pi has no `.mcp.json`
loader and no subagent runner of its own to hand the work to.

## What ports as-is

| Piece | Claude Code | Copilot | pi |
|---|---|---|---|
| Install | `/plugin marketplace add hosom/ossuary` | `copilot plugin install --path …` | `pi install git:github.com/hosom/ossuary` |
| Manifest | `.claude-plugin/plugin.json` | `plugin.json` | `pi` key in `package.json`, or convention dirs (`extensions/`, `skills/`, `prompts/`) |
| Skills | `skills/<name>/SKILL.md` | same | same — pi implements the [Agent Skills standard](https://agentskills.io/specification) and reads `SKILL.md` directories |
| Slash commands | `/ossuary:investigate` | skill invocation | `/skill:investigate`, or a `prompts/*.md` template for a bare `/ossuary-investigate` |
| Agent definition | `agents/*.md` with `name`/`description`/`tools` frontmatter | `agents/*.agent.md`, same fields | same shape: `name`, `description`, `tools`, `model`, body is the system prompt |
| Tool restriction | agent frontmatter `tools:` | agent frontmatter `tools:` | `pi --tools <list>`, which allowlists built-in, extension **and** custom tools |

pi installs packages straight from a git repo, so the marketplace step has an
exact equivalent. `SKILL.md` needs no changes at all — pi even documents pointing
its `skills` setting at `~/.claude/skills`.

## Gap 1: MCP

Ossuary's entire delivery mechanism is a local MCP server. pi does not load
`.mcp.json` and has no MCP client. Two ways across:

**A. Depend on `pi-mcp-adapter`** (npm, v2.15.0, actively maintained). It already
reads `.mcp.json` — the same file the two existing plugins ship — from the
project root, so the config would port verbatim. Two caveats. It defaults to a
*proxy* surface: one `mcp({search, tool, args})` tool instead of individually
named tools, deliberately, to save context. Per-server `directTools: true`
restores individual registration, but then tool names may carry a server prefix
(`ossuary_ossuary_outline`), which is the same class of namespacing problem the
README already documents for Claude Code plugin servers. And it makes Ossuary's
install story "install pi, install this third-party package, install Ossuary".

**B. Ship our own extension.** ~200–300 lines of TypeScript that spawns
`ossuary-mcp`, speaks MCP over stdio, and registers each tool with
`pi.registerTool`. The names stay exactly `ossuary_outline`, `ossuary_read_events`
and so on — which matters, because those names are what the agent files list and
what `tests/test_plugins.py` asserts. No third-party dependency, and the whole
surface stays in this repo where it can be tested.

**Recommendation: B.** It is more code, but it is the only option that keeps the
tool names, the install instructions and the test invariants aligned with the
other two plugins. The cost is real and worth stating plainly: it puts the first
JavaScript into a Python repository, with its own dependency
(`@modelcontextprotocol/sdk`) and its own way of being broken.

## Gap 2: sub-agents

*One session per context window* is a design decision, not a convenience — the
plugins spawn one `session-investigator` per transcript specifically so the second
session is not read by an agent already holding opinions about the first. pi has
no built-in subagent runner.

It does ship a working example of one (`examples/extensions/subagent/`, ~1150
lines), and the mechanism is exactly what is needed:

```
pi --mode json -p --no-session --tools <allowlist> --append-system-prompt <file> "Task: …"
```

Each child is a separate `pi` process, so context isolation is stronger than in
either existing host — a separate process cannot see the parent's conversation at
all. The child loads user-level extensions, so it gets the Ossuary tools; and
`--tools` allowlists extension tools, so *"the read tools and `report_issue` and
nothing else"* is enforceable exactly as it is today. Its agent files are markdown
with `name`/`description`/`tools`/`model` frontmatter, which is the format
`session-investigator.md` is already written in.

So the fan-out is portable, but the runner has to come from somewhere: vendor a
trimmed version of the example into the same extension (~150 lines for what
Ossuary needs — no chains, no parallel UI), or depend on a community package such
as `pi-subagents-j0k3r`. Vendoring keeps it consistent with the recommendation
above.

## What would still differ

Even done well:

- **Slash command names.** pi namespaces skills as `/skill:<name>` and prompt
  templates as `/<filename>`. `/ossuary:investigate` has no exact spelling.
- **The extension is code, not configuration.** The other two plugins are JSON and
  markdown a reader can audit in a minute. This one would ship a process spawner.
  pi's own docs say packages "run with full system access"; ours would too, and
  should say so.
- **`test_plugins.py` would need a third dialect.** It normalises the
  `mcp__<server>__` prefix before comparing toolsets; pi's names are bare, like
  Copilot's, so the shared assertion has room for it — but the spawn path it
  checks is a subprocess argv rather than frontmatter, which is a different kind
  of assertion.

## Decision: the adapter alone

**The host half is not being built.** The adapter is the whole of pi support:
write it, and a pi user investigates their pi sessions from Claude Code or
Copilot, with the plugin that already exists.

Nothing above is load-bearing for that. Ossuary has never required the host to
match the source — a Claude Code user audits their Codex sessions today, and the
corpus statistics are computed *across* sources on purpose. `ossuary_sources`
lists what is on disk regardless of who is asking; discovery, redaction, the
outline and `ossuary_tool_stats` all work from the file. Mixing pi in is a small
gain rather than a compromise: pi's 51200-byte tool cap becomes visible next to
Claude Code's 30000, which is exactly the comparison no single session can show.

What it costs, stated plainly: **someone who runs only pi cannot use Ossuary.**
That is the whole of what the host work would buy, and it can be bought later —
the two halves share no code, so building the extension in six months costs the
same as building it now. What does not wait is the adapter: until it exists, a pi
user pointed at Ossuary finds every session on the machine *except* their own.

The rest of this section stands as the record of what the host route would
involve, so the decision can be revisited without re-deriving it.
